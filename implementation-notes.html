decided places.ts の役割転換: nav producer → geofence 位置/圏内モジュール

placesStatus(表示 doc を返す)を refreshGeofencePosition(signal): Promise<void> に痩せさせた。lastPos 更新 + backoff のみ行い、表示 segment は一切返さない。location.ts が Promise.all 内で副作用として await(place group は geocode+geoinfo のみ)。

Why: 圏内判定(getInsidePlaceIds/getCurrentPlaceId)は lastPos に依存し、それは producer 実行時のみ更新される。表示を消しても位置追跡は要る。codex 助言で「保存地点ゼロなら getPosition しない」「reject は内部で握り locationStatus を巻き込まない」を反映。

decided orphan 掃除 migration migrateDropPlaceNav

既存 config の place group に焼かれた nav 動的 segment(id.startsWith('pl_') / 保存地点 id)と presence(id==='here')を、素材・全 profile の view・glassLayout から除去。温存: config.places / profile.geofence / 他 segment の inPlace 条件。冪等・全 migrate 経路・CONFIG_VERSION 据え置き。

Why: pruneOrphans は source 単位のみ、syncSourceWithStatus は segment 追加のみ(消えた segment を削らない)→ 放置すると layout editor に stale chip が残る。removePlace の掃除を「全 nav + here、ただし geofence は温存」へ一般化。

tradeoff geofence 位置追跡は Location source の poll に連動(parity 維持)

Location を無効化すると lastPos が更新されず geofence が黙って止まる。統合前(places も opt-in client)から同じ挙動なので parity 維持を選択。source-enabled から独立させる案は scope 拡大として見送り(codex も privacy 一貫性から parity 支持)。将来 PositionProvider 共通化は follow-up。

open 「geofence は Location 有効時のみ動く」混乱

place 表示を消したつもりで geofence 自動切替も止まる点が混乱しやすい(codex 指摘)。暫定対応: 保存地点管理 + Add-source の文言で「Requires the Location source enabled」を明示。profile ごとに Location が無効だと geofence 更新が止まるケースは要実機確認。

主要な設計判断

decided source 5 → 1 (client.location)

位置という 1 つの許可・1 つの現在地から派生する 5 系統を、local server が claude/codex/system を束ねるのと同型に 1 source へ。

Why: 同じ許可・現在地・失敗原因を 5 回見せていた。source = フェッチ境界ではなく「producer / 許可 / UX 単位」と再定義(codex)。

deviation group は 5 維持 → 4 → 2(Weather/Place)

当初計画は 5 group 維持。ユーザーの「細分化されすぎ」指摘で 4 group(Weather/Place/Air/Nearby)を経て、最終的に 2 group(Weather=気象+大気質 / Place=地名+標高/TZ+保存地点ナビ)。

Why: Segment.state が per-segment health を持つので「per-group freshness のため group を分ける」必然が消えた。group は純粋に「トグル/glass 行/UI セクションの粗さ」最適化に。codex は当初 2 group に反対(4 推奨)→ display-IA 分離・既定OFF・segment.state を踏まえ撤回し 2 group を支持。

decided built-in 常時ON 化は否 / opt-in 単一 source

Why: 位置は許可必須・通信あり・プライバシー敏感で、builtin Device(無許可・ネット不要・常時on・無効化不可)の契約と非両立。origin: 'app_bundled' で「同梱」性だけ表す。

decided health は segment.state、group.state は派生

各 producer の group.state を、その group 由来の全 segment の Segment.state へ焼く。group.state は「primary(defaultEnabled)segment の最悪状態」で派生。

Why: open-meteo は生きてるが bigdatacloud が死ぬ等を segment 単位で表現。既定OFF の air/nav の error で Weather/Place group 全体が赤くならないよう primary 基準。

decided provenance は view 限定の階層(データに tier 実体を足さない)

Home を Included(builtin + app_bundled client) / Connected(server) でセクション分け。判定は kind + origin。

Why: YAGNI。kind/origin は既存属性。ラベルは "Built-in" でなく "Included"(常時ON 含意を避ける)。Phase 3 で実装。

トレードオフ

tradeoff producer 深いリファクタを避け、orchestrator で再編

src/location.ts が既存 5 producer をそのまま呼び、結果の segment を 2 group に再編。各 producer は独立に getPosition を呼ぶ。

採用理由: テスト済みの整形ロジックを温存し低リスク。maximumAge で OS が位置をキャッシュするため許可ダイアログは実質 1 回。代償: 厳密な「1 回だけ取得」ではない(将来最適化余地)。

tradeoff Place group が静的(地名/標高)+ 動的(保存地点)混在

代償: Place を OFF にすると地名も保存地点ナビも一緒に消える。保存地点距離だけ失敗した時 group が粗く見え得る → primary 基準の group.state で吸収。許容(codex 確認)。
