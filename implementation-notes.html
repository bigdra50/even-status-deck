eveng2-toolbar — 実装ノート

ロードマップ 2 機能の設計・実装ノート。 機能1: バッテリー消耗レート表示（G2 電池の 1% 消費にかかる時間をローカルログから算出し HUD 併記）。 機能2: 表示タイミング条件（segment 単位・閾値 / 更新時 n 秒。将来「上下を向いたら n 秒表示」= IMU consumer もこの上に乗る）。 設計は gpt-5.5 レビュー + ユーザー承認済み。フェーズ分割で実装する。

最新仕様 (2026-05-28 追加): 条件の AND/OR 複合化 + Battery を segment 化

ユーザー要望「segment ごとの条件を AND/OR で複合できるようにしたい」「Battery drain rate を builtin segment の 1 つにし、 G2 Battery % に加え EST(残り時間) も segment として加えたい」を実装。設計は gpt-5.5 と議論済み、drain 表記固定はユーザー確認済み。 未リリース機能の刷新のため後方互換は最小限（既存実機 localStorage の単一条件データだけ migrate で正規化）。

Design decisions

項目決定
条件モデルleaf + 単一 combinator のフラットリスト。VisibilityLeaf = threshold{op,value} | onChange{holdMs}、VisibilityCond = {combinator:'and'|'or'; conditions: VisibilityLeaf[]}。conditions 空 / visibility 未設定 = 常時表示。ネスト木は YAGNI で却下、UI 上限 4 件。
tri-state 評価各 leaf を true|false|'na' に。threshold で percent 不在 = 'na'。'na' 除外後 0 個なら fail-open(true)、それ以外 and=全 true / or=いずれか true。これで OR(threshold欠落, onChange) が常時表示にならず onChange が死なない（gpt-5.5 指摘の修正）。
onChange 状態leaf 単位キー `${segKey}#${i}` で transient 状態を保持。並べ替え/編集で index がずれても transient なので自己回復（stable id は YAGNI）。wakeAt = 活性中 onChange leaf の activeUntil 最小値。
Battery segment 化builtins.localStatus() の hud group を time / date / g2('45%', percent) / drain('↓12%/h') / est('6h') に分割。drain/est は独立に toggle/並び替え/条件を持つ。
emit-only-when-availabledrain/est は算出可能時（level あり・非充電・rate>0 / eta あり）のみ emit。充電/データ不足では segment 不在 → 非描画。既存「server が segment を一時 drop」と同じ経路で、config entry は sync 済みなら温存（toggle/順/条件を保持）。
drain 表記固定ユーザー確認で config.batteryRate（enabled/format 循環）を全廃。drain=↓N%/h、est=Xh 固定。Home の "Battery drain rate" 行・.fmt-btn も撤去。表記制御は各 segment の toggle/条件に一本化。
UI各 metric 行サブ行に複合エディタ。0 件=Show always + "+ Add condition"。1 件=Show when [leaf] [×]。2 件以上で All of/Any of(=and/or) select。threshold は percent を持つ segment のみ候補（drain/est は onChange のみ）。

Deviations / Tradeoffs

箇所内容と理由
CONFIG_VERSION 据え置き（3 のまま）bump すると migrate() が既存 v3 を破壊的に再 migrate するため。同バージョン分岐に normalizeVisibilityAll() を足し、旧 {kind:'always'}→undefined / {kind:'threshold'|'onChange'}→{combinator:'and', conditions:[leaf]} へ正規化、旧 batteryRate フィールドは delete。
cross-metric 条件は非対応条件 metric は self のみ。drain/est は percent を持たないため「G2 電池 % を条件に EST を出す」はできず onChange のみ。self-only を維持する既存方針（[[eveng2-toolbar-roadmap]]）と YAGNI による。将来 metric:'selfPercent'|'g2Battery' 拡張余地あり（gpt-5.5 提案）。
drain/est の表示ラベル暫定 Drain/EST（companion items 表示名）+ 値 ↓12%/h/6h。glass summary では label value 連結で Drain ↓12%/h とやや冗長。

Open questions

  • drain/est の glass 上の表示ラベル/書式（Drain ↓12%/h の冗長さ、EST の ~ 有無）は実機で要確認。
  • onChange を含む複合（特に AND で複数 onChange）の時間遷移は実機 .ehpk で要確認。
  • cross-metric 条件（EST を電池 % でゲート）の需要が出たら metric 拡張を検討。

機能2 旧仕様: 表示条件は segment 単位（group 単位から変更）

当初 Phase B〜D で group 単位の表示条件を実装したが、ユーザー要望 「条件を細かい要素ごとに（memory は memory の値がこうなったら表示）」により segment 単位に置換した（未リリースのため後方互換不要）。下の Phase B/C/D 節は group 単位時の実装履歴。

項目最新仕様
粒度segment 単位。各 segment を自身の値で個別に表示/非表示。SegCfg.visibility?（GroupCfg.visibility は撤去）
metric常に self（その segment 自身）。条件型から segId を drop → always | threshold{op,value} | onChange{holdMs}
評価computeVisibleMap が segment をループ。VisibleMap/VisStates のキーは "src|grp|seg"（segKey）
描画groupLine が enabled かつ可視な segment だけ連結（全部隠れたら group 行は消える）。detail も同様に隠す。buildViews は可視 segment がある group のみ
UI各 metric 行のサブ行に条件エディタ（self なので segment 選択無し）。threshold は percent を持つ segment のみ候補
検証lint/build PASS（132KB）。純粋コア単体 18/18（segment キー・独立性・onChange transient）。ブラウザ end-to-end: mem≥99 で mem だけ消え CPU は残る / 更新時で mem だけ hidden。コンソールエラー無し

Design decisions

項目決定
対象電池G2 のみ。phone 電池は SDK 非対応（device-state の方針踏襲）。
ログ形式level 変化時のみ {level, ts} をリングバッファ(上限 64)に追記し bridge.setLocalStorage 永続。同 level は無視。
レート算出末尾から後方走査で直近の単調減少 run を取り、run 区間の平均（総 drop / 総 span × 3.6e6）= %/h。level 上昇(充電) か gap>2h で run 打ち切り、span<60s はノイズとして null。
ETAcurrentLevel / (%/h) 時間。~6h / ~1h20m 形式。
表記カスタムconfig.batteryRate.format: rate(↓12%/h) / mPerPct(↓8m/%) / eta(~6h) / rateEta(併記, 既定)。companion で循環選択。
充電/データ不足suffix を出さない（''）。充電判定は描画時の現在値で live ゲート（cached とは独立）。

Deviations（計画/素朴な期待から外した点）

箇所変更と理由
CONFIG_VERSION 据え置き（4 にしない）計画では v4 だったが、migrate() は version!==CONFIG_VERSION を旧 machines 形式として扱うため、bump すると既存 v3 config が破壊的に再 migrate され sources/groups を失う。imu と同じく additive optional + ??= 補完で後方互換を保つ。
レート = 中央値 → 区間平均計画は「直近 N 個の 1% 間隔の中央値」。実装は run 全体の平均レート（簡素・堅牢）。外れ値耐性が要れば後で中央値 / EWMA へ。
computeDrainRate から now 引数を削除未使用（ETA は最新 level から算出）。シグネチャ簡素化。
companion applyBatteryRateトグル/表記変更時に setBatteryRateConfig + refreshBuiltins を呼び、共有 battery モジュールへ即反映 + プレビュー更新（glass 不在のブラウザでも config を適用）。

Deviations（意図的に仕様/素朴な期待から外した点）

箇所変更と理由
「左右」= 首かしげ(roll)水平に首を振る yaw は重力ベクトルから原理的に検出不可（ジャイロ積分=ドリフト or フュージョンが必要）。左右は首かしげ(roll)として実装。
軸/しきい値はプレースホルダimuData の軸の向き・スケールが不明なため defaultImuConfig() の値は仮。実機の imu-debug 表示でキャリブレーション前提。
潜在バグ修正を同梱既存 onEvent は未知 sysEvent を全てシングルクリック扱い（idx=0; refresh()）。IMU 有効化で IMU_DATA_REPORT がこれに落ちるとビューリセット + BLE 洪水。click fallback より前に IMU 分岐を追加して遮断。

Tradeoffs（検討した代替案）

  • ユニットテスト vs on-glass デバッグ: 後者を採用（ユーザー選択）。テストランナー未導入のため追加せず。コアは純粋に保ち将来テスト可能。
  • pace 変更のランタイム反映: setImuConfig で axis/thresholds は即反映するが、pace 変更は OFF→ON で再起動が必要（edge、簡素優先）。
  • debug view を巡回に統合 vs 専用モード: 既存のスワイプ巡回機構を再利用（実装簡素）。
  • 電池対策の範囲: 設定トグル（既定 OFF）のみで十分とユーザー決定（2026-05）。auto-stop タイマー・フォアグラウンド限定・UI 警告ラベルは入れない。電池消費が大きいことは把握済みで、常時 ON を避けるのは利用者の明示 opt-in に委ねる。将来 consumer（向いたときのアクション）を設計する段階で、起動方式（イベント駆動で短時間だけ / R1 Ring トリガ等）を併せて検討する。

コミュニティ/公式 調査結果（2026-05）

Zenn・GitHub・公式ドキュメントを調査。未知点は公式・コミュニティとも未文書化で、今回の実装方針（加速度=重力ベクトル前提 + 自前 pitch/roll + 実機キャリブレーション + yaw 非対応）を裏付ける結果だった。

論点調査結果本実装への含意
imuData の正体公式は「3 つの float」とのみ。Zenn 記事(bigdra)はセクション名を「IMU（加速度センサ）」とし accelerometer として扱う。SDK d.ts に gyro/mag/orientation 等の語・別ストリームは無く、単一 {x,y,z} のみ。重力ベクトル前提は妥当。
軸/単位/スケール公式・記事とも記載なし（座標系・g/m·s⁻²・生値の別すべて非公開）。実機キャリブレーション必須は不可避。
ImuReportPace公式「protocol pacing codes, not literal Hz」。Zenn 記事の実測で報告間隔 100ms/500ms/1000ms を確認（非公式）。pace=500 は妥当。
pitch/roll 算出コミュニティ標準は atan2(-x, hypot(y,z)) / atan2(y,z)。G2 専用のヘルパーや姿勢検出サンプルは公式・GitHub とも存在せず自前計算。本実装の anglesOf（atan2 を AxisConfig で一般化）と一致。
yaw / headingG2 ハードウェアは加速度+ジャイロ+地磁気(コンパス)を搭載（公式ブログ）だが、SDK は単一 {x,y,z} しか公開せずジャイロ/磁気の個別ストリーム無し。加速度のみでは yaw 不可。左右=roll の判断が妥当。将来 SDK が磁気/ジャイロを公開すれば yaw 検出の余地あり。
バッテリー消費IMU 有効化は電池を大きく消費。Zenn スクラップ(gpsnmeajp)実測で P1000(1s間隔)でも 10 分で約 10%。常時待機は非現実的。「イベント時に 1 分だけ起動」「R1 Ring 活用」等の工夫が必要との指摘。加えてアプリ稼働中は画面非表示でも消費が増える印象との gotcha も。既定 OFF + 設定トグルで明示 opt-in は必須(実装済)。常時 ON は避ける設計が要る。

up/down/forward（確定）

defaultImuConfig() 確定値: pitchOffsetDeg:-3, rollOffsetDeg:-5.4, pitchUpDeg:10, pitchDownDeg:-13, forwardDeg:6（rollDeg は暫定 15）。app.json → 0.1.10。

left/right（yaw は検出不可）

左右を水平に首を振る(yaw)で行ったため rel_roll が left -0.6°/right +2.7° とノイズ同然で検出不可だった（重力ベクトルが変わらない=加速度の原理的限界）。決定: 左右は首かしげ(roll, 耳を肩へ)で再キャプチャし roll(y) を反応させる。

次: clear log → forward→left(かしげ)→forward→right(かしげ)→forward を各 3-5s 静止でキャプチャ → roll 符号・rollDeg・roll offset を確定。ログは生値なので 0.1.10 .ehpk でそのまま取得可。スマホ #imu-live で値を見ながら可能。

推奨: データキャプチャ → AI 分析（dev server）

目視より確実な方法。ラベル付き IMU サンプルを dev server に集めて、Claude に imu-log.jsonl を分析させ、軸/符号/しきい値を算出する。

要素内容
収集経路アプリ(WebView) → fetch POST {base}/imu-log → Vite plugin(imuLogPlugin) → imu-log.jsonl 追記。ACAO/OPTIONS 対応済み（.ehpk は別オリジンのため）。base = companion の設定済みサーバー source の url（= dev server origin、status fetch と同一）。.ehpk では相対 /imu-log が Mac に届かないため絶対 URL を使う。dev server 直配信時は base 無しで相対送信。
ラベル付けcompanion の IMU capture セクションのポーズボタン[forward/up/down/left/right]。タップで setCaptureLabel、サンプルに label が付く。ポーズ選択時は IMU を自動 ON。
送信imu.ts がキャプチャ中サンプルをバッファし LOG_FLUSH_MS(750ms) ごとに配列で POST。stop / clear log ボタンあり。
分析Claude が imu-log.jsonl を Read → 各 label の x/y/z 平均から gravity/pitch/roll 軸と符号、pitch/roll レンジ → しきい値を提案 → defaultImuConfig() に反映。

キャプチャ手順（.ehpk）

  1. Mac で npm run dev を起動したまま（/imu-log と /api/status を提供）。
  2. 実機に .ehpk をインストール。companion で Mac の dev server URL をサーバー source として登録（status fetch と同じ URL。これがログ送信先 base になる）。capture セクションに log → <url>/imu-log が表示されることを確認。
  3. IMU capture で「clear log」→ 各ポーズボタンをタップし、そのポーズで 3-5 秒静止（forward → up → down → left → right）。最後に「stop」。
  4. 各ポーズ 1 回で十分。迷ったら同じポーズを再タップして追記してよい（label で区別される）。
  5. 「imu-log.jsonl を分析して」と Claude に依頼 → 確定した axis/thresholds を defaultImuConfig() に反映 → rebuild/pack → companion「Reset IMU calibration」で適用。

dev server から直接配信（QR）する場合は base 不要で相対 /imu-log に届くが、ユーザー報告では QR は実機で不安定なため .ehpk + 絶対 URL 経路を推奨。

実機キャリブレーション手順（手動・overlay 目視）

capture を使わない場合の代替。imu-debug overlay の raw x/y/z と pitch/roll を見ながら、軸特定 → デフォルト編集 → Reset 反映 → 体感調整 のループを回す。

Step 1. 軸特定（最重要）

各ポーズで 2-3 秒静止し、imu-debug overlay の値を読む。

ポーズ観察設定（defaultImuConfig().axis）
直立・正面静止x/y/z のうち 1 つだけ大きい値（重力が乗ってる軸）その軸 → gravityFrom。値が負なら gravitySign: -1、正なら 1
上を向く（後ろに ~30°）残り 2 軸のうち動く方その軸 → pitchFrom。pitch が正に増えたら pitchSign: 1、負に行ったら -1
右かしげ（耳を右肩へ）最後に残った軸その軸 → rollFrom。roll が正なら rollSign: 1、負なら -1

規約: pitch>0→up / <0→down、roll>0→right / <0→left、gravityFrom 軸は直立で正に乗る前提（サインで揃える）。

Step 2. 反映方法（持続化の落とし穴）

config.imu はトグルした瞬間に localStorage に永続化されるため、defaultImuConfig() をコード編集してリビルドしても、既存の永続化された値が優先されて新デフォルトが反映されない。

→ companion の 「Reset IMU calibration」ボタン をクリックして config.imu を新しい defaultImuConfig() で上書き保存する。enabled/debug トグル状態は維持される。saveConfig が toolbar:config-changed を発火し、glass 側の onConfigChanged→applyImuConfig→setImuConfig で即座にランタイム反映される。

反復ループ: 軸/値を src/config.ts で編集 → npm run build → deploy → Reset クリック → 確認。

Step 3. しきい値調整（体感）

パラメータ既定調整指針
forwardDeg15°「正面」と判定する余白。揺れで up/down にこぼれるなら拡げ、正面が出にくいなら狭める。forwardDeg < pitchUpDeg/rollDeg を必ず守る（間がヒステリシス余白）
pitchUpDeg / pitchDownDeg±25°深め(±35°) = 意識的に向いたときだけ発火 / 浅め(±18°) = 軽い動きでも
rollDeg25°左右かしげの発火閾値
holdMs800mshold までの保持時間。短すぎ=誤発火、長すぎ=レスポンス悪い
emaAlpha0.3平滑の追従性。フリッカするなら下げる(0.2)、応答が遅いなら上げる(0.4-0.5)

Step 4. 検証

  • 正面静止で dir: forward が安定（フリッカなし）。
  • 各方向を 800ms+ 保持して HELD x.xs が出る。
  • devtools 接続時は [IMU] enter|hold <dir> pitch=… roll=… が console に出る。
