dialog 往復チャネル (はい/いいえ応答を source へ返す・gpt-5.5 と確定)

forward の逆。source が質問を push → ユーザーがリングで選択 → 結果を source へ返す request/response。§10 reserved の POST /api/action を type:"dialog.result" のみ正規化。

decided 結果 endpoint は LAN 受理（forward の emit と非対称）

結果は client（iPhone, LAN）から来るので POST /api/action は loopback でなく LAN を受理。安全性 = server 生成の unguessable requestId（capability token）+ index/action 検証 + accept-once。GET /api/action-result（質問側 watcher の受信）は loopback 限定。

decided requestId は server 払い出し・相関ストアは ring buffer と別

server/actions.ts が pending(requestId/providerId/actions/expiresAt/status/result)を保持。TTL（既定60s）= 表示有効期限 兼 受理期限。event ring buffer は配送、action store は相関で役割分離。

tradeoff 範囲は dialog.result のみ正規化

glass gesture からの任意 source 遠隔操作（type:"source.action"）は §10 reserved のまま。今回は「source の質問への応答」だけを固める。確認 CLI = bun run server ask "..." はい いいえ（選択ラベルを stdout）。

Design decisions (gpt-5.5 と確定)

decided D1 搬送 = cursor 付き long-poll（別 path）

GET /api/events?since=<seq>&waitMs=25000。pending か reset で即返し、無ければ waitMs まで保留。StatusDoc に混ぜない（fire-once と永続状態の混在回避）。SSE/WS は WKWebView の jettison/電池が未検証なので MVP では賭けない。idle churn ~25s/回・イベント時 latency ≈ RTT。

decided D2 取り込み = POST /api/emit（loopback 限定）

外部 watcher が同一ホストから投入。native watcher を server に抱えず分離（OS 依存を隔離）。NDJSON 常駐 provider は後付け adapter で追加可。

decided D3 配送 = source-local seq + (providerId,id) dedupe + ttl ring buffer

client は since cursor と seenId で重複排除。古すぎ/再起動は reset:true で連続性破棄。失効分は配送しない（古い通知を蒸し返さない）。

decided D4 dialog はリモート非対応

notification/toast/banner のみ。dialog は onResult の往復が要るので §10 の POST /api/action 方向で別途扱う。

decided D5 security = loopback emit + rate limit + sanitize

emit は 127.0.0.1/::1 のみ受理（LAN は 403）。providerId 単位 rate limit、body size 上限、文字列 clip/clamp、kind allowlist、空通知破棄。

Deviations (gpt 案からの逸脱・補強)

deviation emit はトークンでなく loopback 限定で守る

gpt は「shared/boot token」も挙げたが、watcher は同一 Mac 常駐なので loopback バインドチェックだけで偽装を防げ、トークン配布の運用を消せる。/api/events は LAN 公開のまま。

deviation events loop は capability 広告 source のみ

補強: client は /api/machine の capabilities.events:true を出す source だけ long-poll する。対応しない source に余計な held 接続を張らない（jettison/電池対策）。

deviation watcher は bun:sqlite でなく sqlite3/plutil CLI

bun:sqlite は bun 専用で型/ランタイムが結合する。macOS 標準の sqlite3（immutable=1 でロックせず読む）+ plutil（binary plist → JSON、失敗時 XML 正規表現フォールバック）にして node/bun 両対応・型問題なしにした。

Tradeoffs

tradeoff long-poll vs SSE/短間隔 poll

long-poll は held 接続だが WKWebView では通常 fetch で、切断時は graceful に再張り。SSE は churn を更に減らすが挙動未検証。短間隔 poll は latency が間隔に律速。→ long-poll を採用、問題が出たら SSE/短 poll に切替可能（別 path なので局所差し替え）。

tradeoff Mac 通知の文面マッピング

overlay の {app,sender,body} に {titl, subt, body} を割当てた。投稿アプリ名（bundle id → 表示名）は引かず、通知の titl を先頭行にした（実用上は送信者/アプリ名が入る）。

Open questions (確認/今後)

  • open Full Disk Access の付与 UX。 watcher を動かすプロセス（ターミナル/bun）に手動付与が要る。案内文は出すが、自動化はしない。
  • open ノイズの多いアプリの除外。 現状は全通知転送。providerId/bundle id 単位の allowlist/denylist は未実装（必要なら config 化）。
  • open since の reload 永続化。 WKWebView reload(=jettison) で loop が since=0 から再開し、TTL 内の通知を再表示しうる。実害小なので未対応。
  • open usernoted スキーマ依存。 macOS 版で record/app 構造や plist キーが変わると watcher が黙って空振りしうる。読めない行はスキップ。

使い方

# 1) サーバー起動 (claude/codex のある Mac)
bun run server          # → http://0.0.0.0:8723 (LAN IP を表示)

# 2) Mac 通知 watcher 起動 (別ターミナル。要 Full Disk Access)
bun run server watch mac-notifications

# 3) 動作確認 (watcher 無しでも curl で overlay を出せる)
curl -X POST http://127.0.0.1:8723/api/emit -H 'Content-Type: application/json' \
  -d '{"providerId":"test","id":"t1","kind":"toast","text":"hello glass"}'
